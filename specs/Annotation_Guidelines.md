# Annotation Guidelines (Руководство по разметке)

Документ описывает правила ручной разметки и верификации данных. 
Несмотря на то, что исходные датасеты получены с
Hugging Face уже с разметкой, команда проводит **повторную ручную верификацию
(re-annotation review)** части выборки в Label Studio для контроля качества
исходных меток, формирования эталонного (gold) подмножества и измерения
согласованности аннотаторов.

---

## 1. Задачи разметки

| Задача | Датасет | Тип разметки | Инструмент |
| :--- | :--- | :--- | :--- |
| Детекция номера | `Car_plate_detecting_dataset` | Bounding box (1 класс) | Label Studio (RectangleLabels) |
| Распознавание (OCR) | `Car_plate_OCR_dataset` | Transcription (текст номера) | Label Studio (TextArea) |

---

## 2. Правила детекции (Bounding Box)

1. **Один класс:** `plate`. Рамка строится строго вокруг номерного знака,
   включая рамку самого знака, но **без** крепёжной рамки/кронштейна автомобиля.
2. **Плотность рамки:** допускается зазор не более 2–3 px от края символов до
   границы bbox. Слишком «свободные» рамки бракуются на review.
3. **Перекрытые/частичные номера (occluded):** рамка строится по **видимой
   части** знака. Поле `occlusion` помечается значением `partial` или `heavy`.
   Если знак перекрыт более чем на ~70% и нечитаем — `occlusion = heavy`.
4. **Несколько номеров в кадре:** размечаются все читаемые знаки отдельными bbox.
5. **Нечитаемый/отсутствующий номер:** изображение помечается тегом
   `no_plate` и выносится на review, в обучающую детекционную выборку не идёт.

## 3. Правила OCR (Transcription)

1. Текст вводится **заглавными латинскими символами** из алфавита
   `1234567890ABEKMHOPCTYX` (12 букв, визуально совпадающих с кириллицей).
2. Регион (2–3 цифры) включается в строку: `A129XY196`.
3. Запрещены пробелы, дефисы, символы вне алфавита. Валидируется regex:
   `^[ABEKMHOPCTYX]\d{3}[ABEKMHOPCTYX]{2}\d{2,3}$`.
4. При неоднозначном символе (грязь, блик, перекрытие) ставится флаг
   `ambiguous = true`, кейс уходит на арбитраж (см. §6).

## 5. Контроль качества (Quality Control)

* **Double annotation:** 10% выборки размечается двумя аннотаторами независимо
  для расчёта метрик согласованности.
* **Метрики согласия:**
  * Детекция — средний **IoU** между bbox двух аннотаторов; порог приёмки
    `IoU ≥ 0.85`.
  * OCR — **Exact Match Agreement** (полное совпадение строки) и **Cohen's κ**
    по согласию символ-в-символ; порог `κ ≥ 0.80`.
* **Auto-checks** перед review (скрипт `validate_annotations.py`):
  координаты bbox в `[0,1]`, площадь > 0, OCR-строка проходит regex,
  отсутствие дубликатов файлов между сплитами.
* **Acceptance gate:** задача принимается, если прошла авто-проверки и
  reviewer подтвердил; иначе возвращается аннотатору с комментарием.

## 6. Спорные кейсы (Disputed cases & Arbitration)

Кейс считается спорным, если выполнено любое из условий:
* `IoU < 0.85` между аннотаторами по детекции;
* несовпадение OCR-строк;
* флаг `ambiguous = true` или `occlusion = heavy`.

Спорные кейсы выгружаются в `reports/disputed_cases.csv`, обсуждаются
арбитром, итоговое решение фиксируется в колонке `final_decision`.
Результаты review агрегируются в `Manual_Labeling_Report.md`.

## 7. Версионирование

Каждый раунд review версионируется тегом `annotation-vN`. Экспорт из Label
Studio хранится в `annotation/label_studio/export_*.json` (JSON-MIN формат),
сконвертированная YOLO-разметка — в `annotation/yolo/`.
