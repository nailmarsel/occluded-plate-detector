Ниже представлено **обоснование выбора инструментов** для проекта.

---

## 1. **Elasticsearch** (включая векторную БД)

**Зачем в проекте:**
- Хранение эмбеддингов (ResNet-108) для миллионов изображений автомобилей.
- Быстрый поиск **top‑5** по косинусному сходству.
- Возможность объединять векторный поиск с атрибутивными фильтрами (цвет, марка, время, камера) – в будущем.

**Почему Elasticsearch подходит:**
- Имеет **встроенную поддержку плотных векторов** (dense_vector) и поиск по ним (cosineSimilarity, dot_product).
- Масштабируется горизонтально, работает с миллиардами векторов.
- Позволяет **одновременно** хранить метаданные (координаты номера, путь к изображению в MinIO, результат OCR, временные метки).
- Используется в production для задач поиска «похожих изображений» (CBIR).
- Легко интеграция с остальным стеком (через REST API, клиенты для Python/Go).
- **Вместе с Kibana** даёт визуализацию и отладку поиска.

---

## 2. **MinIO**

**Зачем в проекте:**  
- Хранение исходных изображений автомобилей, вырезанных автомобилей, вырезанных номеров.
- Доступ к файлам по URL для отображения (top‑5 авто).
- Объектное хранилище, совместимое с S3 API.

**Почему MinIO подходит:**
- Лёгкое развёртывание в Docker-окружении.
- Высокая производительность чтения/записи изображений даже на одном узле.
- S3‑совместимость → можно без изменений кода перейти на AWS S3, если потребуется.
- Идеально для артефактов пайплайна: сохраняем входное фото → вырезанный авто → фото номера.
- Работает в связке с Elasticsearch: в индексе хранится `photo_url` → MinIO возвращает само изображение для фронтенда оператора.

---

## 3. **Kibana**

**Зачем в проекте:**
- Визуализация работы системы:
  - Процент успешно распознанных номеров.
  - Top‑5 запросов – какие авто чаще ищут.
  - Сравнение эмбеддингов (можно посмотреть, насколько правильно работает ResNet).
  - Логи обработки изображений (где YOLO не нашел авто или номер).
- Быстрый просмотр содержимого Elasticsearch без написания кода – отладка.

**Почему Kibana подходит:**  
- Нативная часть стека ELK (Elasticsearch + Kibana).
- Позволяет оператору или разработчику анализировать качество работы нейросетей: ошибки OCR, ложные срабатывания.

---

## 4. **Docker**

**Зачем в проекте:**
- Запуск всех компонентов на одной машине или в кластере:
  - Elasticsearch (+ векторный поиск)
  - Kibana
  - MinIO
  - Python‑сервисы (YOLOv8, ResNet-108, OCR, обработчик конвейера)
- Воспроизводимость окружения, изоляция зависимостей (разные версии PyTorch, OpenCV).

**Почему Docker подходит:**
- Официальные образы Elasticsearch, Kibana, MinIO – готовы к использованию.
- Можно описать `docker‑compose.yml` с сетями, volume для данных.
- Лёгкое масштабирование: если нужно поднять второй экземпляр Elasticsearch.
- Упрощает развёртывание на сервере и на машине разработчика (кроссплатформенно).
- Позволяет версионировать инфраструктуру вместе с кодом.
