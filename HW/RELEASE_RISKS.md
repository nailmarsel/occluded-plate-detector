# Главные риски перед релизом
## Risk Summary

| Категория | Риск | Влияние на релиз | Что сделать перед production-релизом |
|---|---|---|---|
| Data | Датасет мог не покрыть все уникальные случаи, которые встретятся в реальной эксплуатации: редкие ракурсы, частично закрытые номера, грязь, blur, ночная съемка, нестандартное освещение и новые типы изображений. | На новых данных модель может вести себя хуже, чем на учебных и тестовых примерах: пропускать номер, неверно локализовать область номера, ошибаться в OCR или возвращать нерелевантные top-5 результаты. | Расширить validation set сложными и редкими кейсами, отдельно проверять новые типы входных данных и регулярно пополнять датасет примерами из feedback loop. |
| Data | Не все входные случаи были покрыты проверками и тестами: поврежденные изображения, слишком маленькое разрешение, фото без автомобиля, фото без номера, нестандартные форматы и out-of-domain изображения. | В систему могут попадать неподходящие данные. Из-за этого возможны непредвиденные ответы модели: пустой результат, неверный номер, случайное совпадение по embedding, ошибка пайплайна или некорректный ответ API вместо понятного отказа с причиной. | Добавить проверки минимального разрешения, читаемости изображения, лимита размера, наличия автомобиля/номера и корректной причины отказа. Покрыть эти сценарии автотестами. |
| Model | OCR и поиск по частично скрытому номеру пока зависят от качества распознавания видимых символов и ручного `plate_query`. Автоматическое определение скрытых символов и генерация маски работают не полностью. | Для ключевого use case с закрытым номером оператору придется чаще вводить видимый фрагмент вручную. Без этого поиск может перейти в менее точный embedding-only режим или вернуть слишком широкий набор кандидатов. | Добавить occlusion-aware логику: определение нечитаемых зон номера, генерацию маски вида `A8**AA977`, проверку качества masked OCR и отдельные тесты на закрытых номерах. |
| Model | Для модели стоит реализовать больше метрик качества, чем базовые проверки работоспособности. Важно измерять не только общий успех пайплайна, но и качество каждого ML-этапа отдельно. | Без детальных метрик сложнее понять, где именно деградирует система: car detection, plate detection, OCR, embedding search или ранжирование результатов. Это повышает риск незаметной просадки качества после изменения данных или модели. | Добавить регулярный расчет mAP для детекторов, OCR accuracy / character error rate, top-k accuracy для поиска, долю empty plate, low-confidence rate и качество top-5 выдачи на фиксированном наборе. |
| Operations / Monitoring / Rollback | Не полностью покрыт контроль качества инференса, drift-сигналов и отката: нужно точнее отслеживать low-confidence, empty plate, fallback, ошибки по стадиям пайплайна и поведение top-5 результатов. | При деградации OCR, детектора или поиска команда может заметить проблему поздно. Также может быть сложно быстро понять, какую часть системы откатывать и какая версия модели была стабильной. | Расширить inference logging, добавить алерты по error rate / low confidence / empty plate / fallback, фиксировать версию модели в логах и проверить ручной rollback runbook на staging. |
| Operations / Security | В runtime-конфигурации остаются слабые production-настройки: API без авторизации, CORS `*`, Elasticsearch security disabled, статичные MinIO credentials в конфиге. | Для публичного production-доступа это создает риск несанкционированного поиска, индексации, доступа к изображениям и утечки данных. | Для ограниченного MVP держать систему во внутреннем контуре. Перед production добавить auth, secrets management, ограниченный CORS, private object storage policy и аудит доступа. |

## Ключевые риски для release decision

1. **Риск по данным:** датасет мог не покрыть все уникальные случаи, которые появятся в реальной эксплуатации: новые ракурсы, плохое освещение, закрытые области, грязь, blur и out-of-domain изображения. Это напрямую влияет на надежность главного сценария с частично скрытыми номерами.

2. **Риск по модели:** качество нужно контролировать большим набором метрик по каждому этапу: car detection, plate detection, OCR, embedding search и top-5 ranking. Без таких метрик сложно понять, какая часть пайплайна ошибается и как качество меняется после обновлений.

3. **Риск по эксплуатации, monitoring и rollback:** не полностью покрыт контроль low-confidence, empty plate, fallback, ошибок по стадиям и деградации top-5 результатов. При деградации OCR или детектора команда может увидеть проблему поздно и откатывать модель вручную без заранее проверенной процедуры.

## Вывод

Эти риски не блокируют демонстрационный MVP или ограниченный пилот с ручной проверкой оператором. Они блокируют безусловный production-релиз, потому что система работает в чувствительном сценарии идентификации автомобиля и не должна автоматически принимать финальные решения без доказанного качества и наблюдаемого контроля.
